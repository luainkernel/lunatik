    Lua to eBPF by example

    Experimental, as Compiling Lua to eBPF is.

    What a compiled function computes, construct by construct. The table below says what Lua computes, what the eBPF instruction alone would compute and what the compiler emits between the two. Each section after it compiles a program file whose operands come from the packet, so that lunatic folds none of them, lists the object with each instruction annotated, and traces one input to the result. The rows of The Lua a program may use link to these sections.

    What the compiler emits

    A construct the compiler lowers computes what the kernel’s Lua computes, or is refused at its line. Where the eBPF instruction alone computes something else, the compiler emits what lies between:

    Lua Lua computes The instruction alone The compiler emits
    -7 // 2 -4, the floor -3: BPF_SDIV truncates the quotient less one where the remainder is not zero and the signs differ, as luaV_idiv
    -7 % 2 1, the divisor’s sign -1: BPF_SMOD truncates the divisor added where the remainder is not zero and its sign is not the divisor’s, as luaV_mod
    x // -1, x % -1 -x and 0, so math.mininteger // -1 is math.mininteger for math.mininteger, a divide error on x86-64 before Linux 6.12, whose verifier patches the instruction to give math.mininteger and 0, as arm64 always gave a test for -1, then a negation or a zero, as luaV_idiv and luaV_mod take it, so the signed division never meets that case
    x // 0, x % 0 raises 0 and x a test of the divisor, which takes the default verdict
    1 << 64 0 1: the count is masked to 63 the count tested against 64 and -64, past which the result is zero
    1 << -1 0: a negative count shifts the other way math.mininteger: -1 masked is 63 a negative count negated into the other shift; x >> n is x << -n, as in Lua
    x & 0xffffffff the low 32 bits of x x: a 32-bit immediate, sign-extended, reads -1 the constant in a register, by a MOV of its immediate where it fits 32 bits and by LD_IMM64 otherwise
    x + y, x - y, x * y, -x, ~x, the bitwise operators the result wrapped to 64 bits the same one ALU64 instruction; -x a subtraction from zero, ~x an exclusive or with -1
    x < 1 with x at -1 true false under BPF_JLT, which reads -1 as the largest value the signed jump, BPF_JSLT, and its kin for <=, > and >=
    if n then, n a number at 0 taken: 0 is true not taken: the word is zero the jump or nothing, from the register’s type (Branches)
    for i = 1, n, s the iterations counted up front, so the loop never passes n by overflowing a back edge, which the verifier walks iteration by iteration or refuses the count as forprep computes it, with an unsigned division; a bounded loop where the compiler holds the three values, a may_goto header otherwise
    for with a step of 0 raises BPF_DIV by zero gives a count of 0, one pass through the body a step the compiler holds refused, “‘for’ step is zero”, and one the program computes tested, which takes the default verdict
    f(x) the callee’s value, and its raise a call, which answers R0 and nothing else the arguments in R1 to R4, the address of the caller’s flag after them, and the flag read after the call
    p:getint16(n) two bytes at n, signed; raises past the packet a load the verifier refuses until the program tests the end the offset tested unsigned against 65535 less the width, the end against data_end, and the sign extended by a shift left and an arithmetic shift right, where BPF_MEMSX would extend it
    #p the bytes the data object views no instruction: the context holds the two bounds data_end less data, both read from the context
    skb:data() on an skb that is not linear raises in a tc callback data_end ends the linear head, short of the packet len compared with the head’s length, which takes the default verdict where they differ
    skb:priority(v) raises outside 0 to U32_MAX a four-byte store keeps the low 32 bits a value the compiler holds checked against the field’s width, and one the program computes tested, which takes the default verdict
    m[k] the value, or nil the helper answers a pointer, or NULL, which the verifier lets the program read only past a test the helper, and a value typed “value or nil” until if v then reads it, on the branch that found it
    m[k] = v, m[k] = nil the kernel’s bpf.map raises when the map refuses the update, or refuses the delete for any reason but an absent key the helper’s return code the helper, and the default verdict on any code but zero, or -ENOENT from a delete
    m[k] with k outside the key’s spec string.pack raises a store that keeps the low bytes a key the compiler holds packed when the function is compiled, and one the program computes tested, which takes the default verdict; a value alike
    v.field of a struct value the field the codec decodes a load the verifier refuses until the program tests the lookup a load at the field’s offset and width, the sign extended where the field is signed

    The shift pair stands for BPF_MEMSX, which the s390 JIT of 6.6 does not take. A read is of the kernel’s byte order on both sides: the kernel’s data object reads one so, and a map spec of another order is refused when the body declares it.

    The sources are lua/lvm.c, luaV_idiv, luaV_mod, luaV_shiftl and forprep; the eBPF instruction set, for BPF_SDIV, BPF_SMOD, the shift mask, the zero divisor and BPF_MEMSX; bpf: Fix a sdiv overflow issue, for math.mininteger over -1; and kernel-notes.md, Rules that shape the subset and The packet a network program reads.

    Reading a listing

    A listing is llvm-objdump -d of the object lunatik bpf writes, with the hexadecimal left out, each jump given its target, and the Lua line each instruction came from. That line is in the object’s .BTF.ext, which llvm-objdump does not read: the verifier’s log quotes the same lines, and so does bpftool prog dump xlated of a loaded program, after the kernel has rewritten its context reads. An llvm-objdump that predates the instructions Linux 6.6 added, LLVM 14’s among them, prints a signed division as an unsigned /= and a signed modulo as <unknown>; the listings write them s/= and s%=.

    The registers:

    • r1 holds the context when the program starts, and r0 what it returns.
    • r6 to r9 hold Lua registers 0 to 3, the function’s first locals, and a call leaves them alone. Lua registers 4 and up live in the frame, at r10 - 40, r10 - 48 and on down.
    • r10 is the frame. r10 - 8 holds the flag a called function raises, r10 - 16 the address of its caller’s flag, and r10 - 24 and r10 - 32 the key and the value a map helper takes.
    • r1 to r5 hold what one line computes.

    Every listing ends with the instructions where the function stops: the default verdict, and the exit.

    The packet

    A packet read, p:getuint16(16), held to the bounds of the packet:

    local xdp = require("bpf.xdp")

return xdp.program(function(ctx)
    local p = ctx:packet()
    local length = p:getuint16(16)
    return length
end)

    Byte 16 of an Ethernet frame that carries IPv4 is the total length of the IPv4 packet, two bytes in network order.

          line 3: return xdp.program(function(ctx)
   0  r6 = r1                       ctx
      line 4: local p = ctx:packet()
   1  r8 = r6                       the packet: the context register
   2  r7 = r8                       p
      line 5: local length = p:getuint16(16)
   3  r9 = r7
   4  r1 = 16
   5  *(u64 *)(r10 -40) = r1
   6  r4 = *(u64 *)(r10 -40)        the offset
   7  r1 = *(u32 *)(r9 +0)          xdp_md.data
   8  r2 = *(u32 *)(r9 +4)          xdp_md.data_end
   9  if r4 > 65533 goto 18         past 65535 less the width: stops
  10  r1 += r4                      data + 16
  11  r4 = r1
  12  r4 += 2
  13  if r4 > r2 goto 18            past the end of the packet: stops

    Instruction 13 is the test the verifier asks for before instruction 14 reads: it takes the load only on the path where data + 16 + 2 is not past data_end. Instruction 9 stops the program at an offset no packet reaches, and at a negative one too, since the test is unsigned. A signed read, p:getint16(n), adds a shift left and an arithmetic shift right after the load, as instructions 15 and 16 of Floor division and modulo do for a byte. #p is data_end less data, both read from the context.

    Frame Instructions What they compute The program returns
    34 bytes, IPv4, total length 00 1c, 28 13, 14 18 is within 34; 00 1c read little-endian 7168, 0x1c00
    14 bytes, an Ethernet header alone 13 18 is past 14 2, XDP_PASS

    The kernel’s Lua reads the same 7168 from p:getuint16(16) on arm64 and x86. Read a byte at a time, p:getbyte(16) << 8 | p:getbyte(17), the length is 28 on every kernel.

    Arithmetic

    a + b, a - b, a * b and the bitwise operators are one ALU64 instruction each, as instruction 30 of Loops adds a byte to s; -a is a subtraction from zero and ~a an exclusive or with -1. A constant that does not fit 32 bits signed is loaded whole, by LD_IMM64. //, % and the shifts compute something else than the instruction alone, and the compiler emits what lies between.

    Floor division and modulo

    local xdp = require("bpf.xdp")

return xdp.program(function(ctx)
    local p = ctx:packet()
    local a = p:getint8(14)
    local b = p:getint8(15)
    return a // b
end)

    a and b are read from the packet, so lunatic folds nothing and the division is compiled. In the kernel’s Lua a / b is a // b, and it compiles to the same instructions.

    Shifts

    The same program with return a << n, n read from byte 15; instructions 0 to 33 read a and n:

          line 7: return a << n
  34  r1 = r8                       a
  35  r2 = r9                       n
  36  if r2 s< 0 goto 40            a negative count shifts right
  37  if r2 s>= 64 goto 44          64 or more: every bit shifted out
  38  r1 <<= r2
  39  goto 45
  40  if r2 s<= -64 goto 44         -64 or less: every bit shifted out
  41  r2 = -r2
  42  r1 >>= r2                     logical: Lua fills with zeros
  43  goto 45
  44  r1 = 0
  45  *(u64 *)(r10 -40) = r1
  46  r0 = *(u64 *)(r10 -40)
  47  r0 = r0
  48  exit
      line 8: end)
  49  r0 = 2                        XDP_PASS, the default verdict
  50  exit

    This is Lua’s luaV_shiftl. BPF_LSH alone masks the count to its low six bits, so 1 << 64 would give 1, and 3 << -1, a shift by 63, math.mininteger. Bytes 14 and 15 at 03 ff, so a is 3 and n is -1:

    Instructions What they compute Value
    36 -1 is negative jump to 40
    40 -1 is above -64 no jump
    41 the count negated r2 is 1
    42 3 >> 1 r1 is 1
    45 to 48 r0 is 1 the program returns 1

    Lua computes 3 << -1 as 1. With 1 and 64, instruction 37 jumps to 44, and the program returns 0. a >> n is a << -n, as in Lua: the count is negated first, and the same tests follow.

    Comparisons and truth

    local xdp    = require("bpf.xdp")
local action = require("linux.xdp").action

return xdp.program(function(ctx)
    local p = ctx:packet()
    local a = p:getint8(14)
    local small = a < 1
    local n = p:getbyte(15)
    if n and small then
        return action.DROP
    end
    return action.PASS
end)

    a < 1 is signed, as every comparison of Lua integers is. n is a number, and a number is true in Lua, 0 included, so n and small is small: the compiler knows it from the type of n, and tests small alone. Instructions 0 to 17 read a into r8.

A variable that holds a number on one path and nil on another has no such reading, since the kernel holds nil, false and 0 as the same word, and a test or an == of it is refused.

    Values of the body

    Maps

    local map    = require("bpf.map")
local xdp    = require("bpf.xdp")
local action = require("linux.xdp").action

local seen = map.hash("seen", {key = "I4", value = "I8", entries = 256})

return xdp.program(function(ctx)
    local p = ctx:packet()
    local proto = p:getbyte(23)
    local n = seen[proto]
    if n then
        seen[proto] = n + 1
    else
        seen[proto] = 1
    end
    return action.PASS
end)

    seen[proto] is a lookup, whose value is a number or nil until if n then tests it.     Instruction 28 reads the value only past instruction 27: the verifier refuses a read through a pointer that may be NULL, and the compiler refuses to use n before if n then tests it. Four frames, one after the other, over a map that starts empty:

    Frame Byte 23 Path seen after
    IPv4, TCP 6 27 jumps: nil, so 54 to 70 store 1 {[6] = 1}
    the same again 6 27 goes on: 1, so 32 to 52 store 2 {[6] = 2}
    ARP, 42 bytes 0 nil, so 1 is stored {[6] = 2, [0] = 1}

    Each run returns 2. A kernel script reads the same map with the kernel’s bpf.map, as map.hash("/sys/fs/bpf/lunatik/<script>/seen", "I4", "I8"). A struct value is read a field at a time, by a load at the field’s offset and width.

    Loops

    local xdp = require("bpf.xdp")

return xdp.program(function(ctx)
    local p = ctx:packet()
    local s = 0
    for i = 14, 17 do
        s = s + p:getbyte(i)
    end
    return s
end)

    The compiler holds the three values, 14, 17 and 1, so it counts the passes when it compiles, as Lua’s forprep counts them when it runs: (17 - 14) // 1 is 3 more after the first. The loop is a back edge, which the verifier walks pass by pass. In Lua 5.5 a loop takes three registers, the count, the step and i: here r9, r10 - 40 and r10 - 48. Instructions 0 to 2 take ctx and p.

    Bytes 14 to 17 at 01 02 03 04 make four passes, i at 14, 15, 16 and 17, and the program returns 10. A 16-byte frame stops at the third pass, whose read of byte 16 is past the packet, and returns 2, XDP_PASS.

    With a bound the program computes, for i = 1, n do, the count is computed when the loop starts, with an unsigned division as forprep does, and the back edge passes through may_goto, which the kernel takes from Linux 6.9: the kernel leaves the loop there once the budget it gives the loop runs out (#1944). Compiled for an earlier kernel, the loop is refused: “a ‘for’ the compiler cannot bound needs may_goto, which this kernel lacks”.

    Calls

    local xdp = require("bpf.xdp")

local function half(n, d)
    return n // d
end

return xdp.program(function(ctx)
    local p = ctx:packet()
    local a = p:getint8(14)
    local b = p:getint8(15)
    local v = half(a, b)
    return v
end)

    half is compiled once, as a BPF-to-BPF function in the section .text. Its arguments go in r1 and r2, and the address of the caller’s flag in the register after them, r3. Instructions 0 to 33 of the program read a and b.

    Bytes 14 and 15 at 07 00: a is 7 and b is 0. In half the zero test jumps to 22, which raises the flag and returns; at 43 the program reads the flag and jumps to 48, so it returns 2, XDP_PASS, as if the division had been in the program’s own function. With -7 and 2, half returns -4, and so does the program.

    The call returns to the program, which reads the flag before it goes on. return half(a, b) would be a tail call, which Lua runs without coming back, and is refused: “a tail call cannot be compiled”.
