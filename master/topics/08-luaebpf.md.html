    Compiling Lua to eBPF

    Experimental. The compiler and what a program file reaches through it, lunatik bpf, lunatik run --dev, the modules a program file’s body requires and the part of Lua it compiles, may change in a minor release.

    A program file is a Lua file whose functions become eBPF programs, which the kernel runs natively on each packet a device receives or sends. lunatik bpf compiles it on the host, lunatik run --dev attaches it, and a map it declares is shared with the kernel scripts. This page is for the author of a program file, who knows Lua: what a program computes, when it stops and when it is refused. Lua to eBPF by example lists what each construct compiles to, and how the compiler is built is in its design notes.

    A first program

    This program counts the IPv4 packets that reach a device, by protocol, in a map a kernel script reads.

    protocols.bpf.lua:

    local map    = require("bpf.map")
local xdp    = require("bpf.xdp")
local action = require("linux.xdp").action
local eth    = require("linux.eth").proto

local ETHERTYPE <const> = 12 -- the ethertype, in network order
local PROTOCOL  <const> = 23 -- the protocol byte of the IPv4 header

local counts = map.array("counts", {key = "I4", value = "I8", entries = 256})

return xdp.program(function(ctx)
    local p = ctx:packet()
    if p:getbyte(ETHERTYPE) << 8 | p:getbyte(ETHERTYPE + 1) == eth.IP then
        local protocol = p:getbyte(PROTOCOL)
        local n = counts[protocol]
        if n then
            counts[protocol] = n + 1
        end
    end
    return action.PASS
end, {default = action.PASS})

    The file has two parts. Its body, every line outside the function, runs once, on the host, when the file is compiled: it declares the map counts and the program, with the verdict a return with no value gives. The function is the program: it is compiled to eBPF and runs in the kernel on each packet. It returns XDP_PASS, so every packet it can read goes on to the network stack.

    Compile it into place and attach it to a device:

    sudo lunatik bpf -o /usr/local/lib/bpf/luaebpf/protocols.bpf.o protocols.bpf.lua
sudo lunatik run --dev=eth0 protocols

    lunatik run creates the map and pins it at /sys/fs/bpf/lunatik/protocols/counts, where a kernel script opens it with the kernel’s bpf.map. lunatik -e runs one such chunk, which prints the TCP and the UDP packets counted so far:

    sudo lunatik -e 'local map = require("bpf.map")
local ipproto = require("linux.socket").ipproto
local counts <close> = map.array("/sys/fs/bpf/lunatik/protocols/counts", "I4", "I8")
return counts[ipproto.TCP], counts[ipproto.UDP]'

    A frame that says IPv4 but is shorter than 24 bytes has no byte 23: its read stops the program, which returns XDP_ABORTED, so the frame is dropped and nothing is counted. The lookup and the update are two steps, so two CPUs that count the same protocol at once can lose one of the increments.

    sudo lunatik stop protocols

   XDP  PASS DROP TX REDIRECT ABORTED act as named
   TC   OK SHOT REDIRECT act as named; the rest of linux.tc.action

   where the program computes a value that is no action, and where

    A program returns its verdict, which tells the kernel what to do with the packet: a value of linux.xdp.action in an XDP program, of linux.tc.action in a TC one, the values a kernel script’s callback returns on the same hook.

    • In an XDP program, PASS, DROP, TX, REDIRECT and ABORTED act as the kernel defines them.
    • In a TC program, OK lets the packet go on, SHOT drops it and REDIRECT redirects it. The rest of linux.tc.action decides nothing: UNSPEC hands the packet to the next TC program on the device, and every other action skips those programs; either way the packet then goes on, through the device’s tc filters if it has any.
    • A value the program computes that is none of these, return v where v is a byte past 4 in an XDP program, stops the program, as the kernel’s Lua answers a callback returning it with the hook’s fallback, the answer it gives a callback that raised. One the compiler knows is refused, “the verdict 11 is not an XDP action”, and so is a boolean, which no action is: return p:getbyte(23) == ipproto.TCP gives “the verdict may be a boolean here; return an action”.

    A return with no value, or with nil, returns the default verdict. A verdict that may be nil is refused: “the verdict may be nil here; test it first”. The constructor names the default verdict, an action, and a constructor that names none is refused at the line of the program’s function:

    return xdp.program(filter, {default = action.DROP})

    A program that stops, where Lua would raise, where the verdict it computed is no action or where a for outruns the budget the kernel gives it, does not return its default. An XDP program returns XDP_ABORTED, the kernel’s verdict for a program error, which drops the packet and, in the generic path and in most drivers, fires the tracepoint xdp:xdp_exception; a TC program, whose type has no such verdict, returns TC_ACT_SHOT, which drops the packet. A packet the program cannot read is dropped, whatever its default: a program that must let it through tests #p before it reads. A default that is not an action is refused: “xdp.program’s default verdict is not an XDP action”. A value the program computes reaches a kernel script through a map, or as the argument of a call into a runtime, not through the verdict.

    Where Lua would raise an error, and where the part of Lua the compiler takes ends, a program file fails in one of three places.

    • Refused. lunatik bpf prints lunatik: <file>:<line>: <reason>, exits 1 and writes no object. What the subset does not compile is refused, and so is an operation the compiler can see is wrong because it knows the value: a for step of 0, a map key or value its spec cannot pack, a skb:priority outside 0 to 4294967295, a verdict that is no action of its program type.
    • Refused at load. The kernel’s verifier checks the object again when lunatik run loads it. A program past the verifier’s limits, most often a loop of many passes, is refused there: lunatik run prints the verifier’s log, which quotes the Lua lines, exits 1 and leaves nothing attached. A call into a runtime whose module carries no BTF is refused there too, by libbpf, whose warning names the kfunc (Calls into a kernel Lua runtime), and so is one under a license the kernel does not count as GPL-compatible (The license).
    • Stops. In the kernel, on a packet, the program returns at once XDP_ABORTED in XDP or TC_ACT_SHOT in TC, which drop the packet, and nothing is logged (#2098); a tracer reads an XDP program’s stops at the tracepoint xdp:xdp_exception. A program stops at a read past the packet, a division or a modulo by 0, a for step of 0 it computed, a for whose passes outrun the budget the kernel gives it, a map key or value its spec cannot pack, a map update or delete the map refuses, a skb:priority it computed outside 0 to 4294967295, a verdict it computed that is no action of its program type, and in a function it called that stops. A division by a 0 the compiler knows is not refused: the program stops on every packet that reaches it.

    The packet

    A program’s argument is its context, which offers the methods of the kernel’s own object for the hook, and opens the packet:

    Program The context offers
    XDP ctx:packet(), the packet; ctx:ingress(), the index of the device it arrived on; ctx:queue(), the receive queue it arrived in
    TC skb:data(), the packet; #skb, its length; skb:ifindex(), the index of its device; skb:hash(), its flow hash; skb:priority(), its priority, which skb:priority(v) sets and returns

    Any other method is refused: skb:mark() gives “the context has no method ‘mark’”. The packet is a read-only view of its bytes, with the reads of the kernel’s data object. An offset counts from 0, the first byte of the Ethernet header. On TC the packet is the whole skb, the bytes past its linear head included, as the kernel’s skb:data() reads it in a tc callback: a segment the host sends carries its payload there, and #p is #skb.

    Method Reads
    p:getbyte(n), p:getuint8(n) 1 byte, unsigned
    p:getint8(n) 1 byte, signed
    p:getuint16(n), p:getint16(n) 2 bytes, unsigned or signed
    p:getuint32(n), p:getint32(n) 4 bytes, unsigned or signed
    p:getint64(n) 8 bytes, signed
    #p the length of the packet

    A read wider than a byte is in the byte order of the kernel, as the kernel’s data object reads it: little-endian on x86 and arm64, where p:getuint16(16) of an IPv4 header whose total length is 28 gives 7168. A field in network order is read a byte at a time:

    local length = p:getbyte(16) << 8 | p:getbyte(17) --> 28

    A read that passes the end of the packet stops the program, and so does an XDP read that starts past byte 65535 less its width. There is no getuint64, since a Lua integer is signed, and no write: “the packet has no method ‘setbyte’”. The bounds of the packet are not numbers: ctx.data_end - ctx.data is refused, “‘data_end’ is a packet bound, not a number; ‘#’ on the packet is its length”. On a kernel without efficient unaligned access, an XDP read wider than a byte is refused (#2047): “‘getuint16’ reads more than a byte, and this kernel lacks efficient unaligned access”; a TC read is not, since it copies its bytes before it reads them. skb:data(layer) is refused: “‘data’ with a layer is not compiled yet”.

    Maps

    The body declares a map with bpf.map: map.hash(name, spec), map.array(name, spec) or map.lru_hash(name, spec). The spec is {key = ..., value = ..., entries = ...}: the key is a string.pack format of one integer, four bytes wide in an array, the value one of those or a struct codec, both in the kernel’s byte order but for a field the codec’s layout marks bigendian, and entries the map’s capacity. lunatik run creates the map and pins it at /sys/fs/bpf/lunatik/<script>/<name>, where a kernel script opens it with the constructor of the same name of the kernel’s bpf.map, which takes the path and the two specs: map.hash(path, "I4", "I8").

    In a compiled function a map reads as a table.

    • m[k] is the value, or nil. The value is used only after if v then, or if not v then, tests it; any other use is refused: “‘flows’ may be nil here; test it first”. A lookup in an array within its entries always finds a value, 0 where nothing was written.
    • m[k] = v inserts or replaces the entry, and m[k] = nil deletes it; deleting a key the map does not hold is not an error.
    • A key or a value its spec cannot pack stops the program, and so does an update or a delete the map refuses: an update of a full hash map, an index past an array’s entries, a delete from an array. One the compiler knows is refused: “the map key -1 does not fit ‘I4’”.
    • A struct value is read-only and read by field name, v.ttl, as its codec decodes it: a field the layout marks bigendian, as luaebpf.vmlinux.layout marks a __be16, reads most significant byte first, so v.tot_len of an IPv4 header whose total length is 28 is 28. A field wider than a byte is refused on a kernel without efficient unaligned access, as a packet read is.

    Calls

    A compiled function calls a Lua function the program file declares, or one a kernel script it requires declares, installed as source. The callee is compiled once for each program that calls it.

    • It takes at most four arguments, each a number or the packet, and returns one value; Lua’s nil fills every other result the caller asks for.
    • Its first call fixes the types of its arguments: a later call with other types is refused, “‘f’ is called with a packet and compiled with a number”.
    • A callee that stops stops the program.
    • A function written in C is refused, print, pcall, ipairs and math.floor among them: “‘print’ is not a Lua function this program file declares”. So is recursion, “recursion through ‘walk’”, and a call whose arguments include a call, f(g(x)), which is written local y = g(x) and then f(y).
    • return f(x) is a tail call, which is refused: write local v = f(x), then return v.

    Calls into a kernel Lua runtime

    A program hands a packet to Lua by calling a kernel Lua runtime, a kernel script run in softirq context whose callback decides the packet. The body names the runtime with lunatik.runtime(script), of lunatik, the compile-time twin of the kernel’s: script is the script the runtime runs, its path below /lib/modules/lua/ without .lua, as lunatik run takes it, and nothing else ties the program to the runtime. The program calls the runtime’s run method, whichever its type. This program file hands Lua the UDP frames, and the kernel script drops one to port 53 longer than 512 bytes:

    ports.bpf.lua:

    local xdp     = require("bpf.xdp")
local lunatik = require("lunatik")
local action  = require("linux.xdp").action
local eth     = require("linux.eth").proto
local ipproto = require("linux.socket").ipproto

local ETHERTYPE <const> = 12 -- the ethertype, in network order
local PROTOCOL  <const> = 23 -- the protocol byte of the IPv4 header
local PORT      <const> = 36 -- the UDP destination port, past an IPv4 header with no options

local limits = lunatik.runtime("limits")

return xdp.program(function(ctx)
    local p = ctx:packet()
    if p:getbyte(ETHERTYPE) << 8 | p:getbyte(ETHERTYPE + 1) ~= eth.IP or p:getbyte(PROTOCOL) ~= ipproto.UDP then
        return action.PASS
    end
    local port = p:getbyte(PORT) << 8 | p:getbyte(PORT + 1)
    local verdict = limits:run(port, #p)
    if verdict then
        return verdict
    end
    return action.PASS
end, {default = action.PASS})

    limits.lua, the kernel script:

    local xdp    = require("xdp")
local action = require("linux.xdp").action

local WORD <const> = 8

local longest = {[53] = 512} -- the longest frame a port takes

local function callback(ctx)
    local argument = ctx:argument()
    local port, length = argument:getint64(0), argument:getint64(WORD)
    local limit = longest[port]
    if limit and length > limit then
        return action.DROP
    end
end

xdp.attach(callback)

    sudo install -m 0644 limits.lua /lib/modules/lua/limits.lua
sudo lunatik bpf -o /usr/local/lib/bpf/luaebpf/ports.bpf.o ports.bpf.lua
sudo lunatik run --context=softirq limits
sudo lunatik run --dev=eth0 ports

    The first lunatik run starts the runtime and the second attaches the program, which calls limits whatever its own name. The callback returns nothing for any other frame, so the call answers nil there, and the program passes the frame.

    • limits:run(a, b), in the program’s own function, runs the callback with the context of the packet the program runs on, ctx:packet() in an XDP callback and ctx:skb() in a TC one, and with the arguments, each a number, as 64-bit integers in order: ctx:argument() holds 8 bytes for each, which ctx:argument():getint64(0), getint64(8) and on read, and is empty for limits:run(). A call from an XDP program reaches the callback xdp.attach registered, and one from a TC program the callback of tc.attach.
    • The call answers the callback’s verdict, a value of linux.xdp.action or linux.tc.action, or nil where none comes back: no runtime of that name runs in softirq with a callback attached, or the callback raises, returns nil or nothing, or returns what is not one of the hook’s actions, UNSPEC included in a TC one. A runtime of process context is never called, and the module logs “‘limits’ is a process-context runtime, not dispatched”; a value that is not an action is logged as “invalid action”. The call never stops the program.
    • The answer is used only after if v then, if not v then, v == nil or v ~= nil tests it, which gives the verdict on one branch and nil on the other, a nil the program may return as its default verdict. v = v or action.PASS is such a test, since Lua compiles it as one. Any other use is refused, “‘limits’ may be nil here; test it first”, and an ordered comparison “attempt to compare a runtime answer with a number”.
    • A call in a function the program calls is refused, “‘limits’ can only be called from the program’s own function”, since only the program’s own function holds the context, and so is one in a program whose parameter does not hold it, “a call into the runtime passes the context, which the program’s parameter does not hold”. An argument that is not a number is refused, “argument #1 is a boolean, and a call into the runtime passes numbers”, and so is a lunatik.runtime with no script, at its line, “lunatik.runtime takes a script”. A call of the runtime itself is refused, “a runtime is called through its method; write ‘limits:run(…)’”, and so is any other method, “a runtime has no method ‘call’; write ‘limits:run(…)’”.
    • The name and the arguments are written on the program’s stack while the call runs, 512 bytes it shares with the function’s own values; a call they do not fit is refused, “the function needs 528 bytes of stack, over the 512 eBPF allows”, one with a name of 480 bytes among them.
    • Each call runs the kernel’s Lua interpreter on the packet path, the cost of a Lua call on every packet that reaches it: a program decides what it can by itself, a map in front, and calls Lua for the rest. lunatik bpf prints on stdout a line for each call it compiled, <file>:<line>: calls the runtime '<name>', in the order it met them, and nothing for a file with none; for the file above, ports.bpf.lua:19: calls the runtime 'limits'.
    • The object loads where the module of its call, luaxdp or luatc, carries BTF, which a module built after sudo make btf_install does. Where it carries none, lunatik run prints libbpf’s “extern (func ksym) ‘bpf_luaxdp_run’: not found in kernel or module BTFs”, exits 1 and leaves nothing attached.

    Loops

    A numeric for is the only loop compiled. It makes the passes Lua makes.

    • With bounds and a step the compiler knows, for i = 14, 17 do, it compiles for every kernel. The verifier walks it pass by pass when lunatik run loads it, so a loop of many passes is refused there: for i = 1, 100000 do gives “BPF program is too large”, and one that reads the packet on each pass “The sequence of 8193 jumps is too complex”, at fewer passes.
    • With a bound or a step the program computes, for i = 1, n do, it compiles for every kernel. The kernel’s iterator counts its passes, 8,388,609 at most, and a loop that would make more stops the program before its first pass. The iterator is a kfunc, which the kernel lets a program call only under its JIT: with net.core.bpf_jit_enable at 0 the load is refused, “JIT is required for calling kernel function”, and on an architecture whose JIT calls none, “JIT does not support calling kernel function”. From Linux 6.9 each pass also goes through the kernel’s may_goto, which gives the loops of one call of a function a budget they share, each call starting it in full: about a quarter of a second where the kernel’s JIT times the loops, x86 from 6.15 and arm64 from 6.18 among them, and 8,388,608 passes after the first elsewhere, which one loop alone never spends. The program stops once it runs out, where Lua would make every pass. From 6.17 a kernel that times them writes “ERROR: Timeout detected for may_goto instruction” to the program’s stderr stream when it stops one. Before 6.9 nothing bounds the time, so loops nested in one another make every pass they count.
    • The verifier walks such a loop until a pass ends as an earlier one did, and a value the body carries from pass to pass, read by a later test the verifier decides, never ends one so. A count of the bytes that match, n = n + 1 in the body and if n > 3 then after the loop, is such a value, since the verifier knows n on every pass, and so is a sum of the packet’s bytes returned as s & 3, whose verdict test it decides from the two bits: each is refused at load, “The sequence of 8193 jumps is too complex” or “BPF program is too large”. The same sum tested with if s > 100 then loads, and so does a flag the body sets, found = true, tested after the loop.
    • A step of 0 is refused when the compiler knows it, “‘for’ step is zero”, and stops the program when the program computes it.

    while, repeat, a goto backwards and a generic for are refused.

    The license

    The object declares one license for its programs, which the kernel reads when lunatik run loads them. A program file names it in the options its constructors take, license, a string, and a file that names none declares Dual MIT/GPL:

    return xdp.program(filter, {default = action.DROP, license = "GPL"})
    • Every program of a file carries the license the object declares, since libbpf loads each under the object’s one license section. A constructor whose license is not the one of the programs before it is refused at the line of its function, a program that names none counting as Dual MIT/GPL: “tc.program’s license ‘GPL’ is not ‘Dual MIT/GPL’, the license of the programs before it”. So is a license that is not a string, “xdp.program’s license is not a string”. Any string compiles, and libbpf keeps its first 63 bytes.
    • The kernel reads the string for one thing, whether the program is GPL-compatible, which it is under GPL, GPL v2, GPL and additional rights, Dual BSD/GPL, Dual MIT/GPL and Dual MPL/GPL (license_is_gpl_compatible, include/linux/license.h) and under no other string. It keeps that alone: bpftool prog show prints gpl for a GPL-compatible program, and the string is read from the object, readelf -p license protocols.bpf.o.
    • A program that calls a kernel function loads only under a GPL-compatible license, and a call into a runtime is such a call. Under any other, lunatik run prints the verifier’s “cannot call kernel function from non-GPL compatible program”, exits 1 and leaves nothing attached. A program that calls none, which reads its packet and its context and looks up and updates its maps, loads under any license.

    Where a compiled function and Lua differ

    Lua decides some things only when the line runs, from the type a value has then. A compiled function cannot, and is refused where its answer could differ from Lua’s. A variable that holds a number on one path and nil or a boolean on another is refused where == compares it or if tests it, since the kernel holds nil, false and 0 as the same word:

    local v
if p:getbyte(14) > 0 then v = 7 end
if v == 7 then return action.DROP end -- "a number that may be nil cannot be compared with a number here"

    Give the variable one type on every path: local v = 0. These are refused too:

    • The value of a map lookup used before if v then: “‘flows’ may be nil here; test it first”. The kernel lets the program read the value only past that test.
    • A variable that holds a lookup in one map on one path and in another map on the other: “a map value here comes from more than one map”. Which map it came from decides how its value is read.
    • A variable that holds the answer of a call into a runtime on one path and another value on the other, tested where the two paths meet: “a runtime answer joined another value here, whose nil is 0 and not -1; test it before the paths join”. The kernel holds the answer’s nil as -1 and every other nil as 0, and the word does not say which path it came from. Tested on the path of the call, the answer is a verdict or the nil every other path holds, and the paths join as any two do.
    • A verdict that may be nil: “the verdict may be nil here; test it first”. The kernel would read nil as 0, which is an action.
    • A verdict that may be a boolean: “the verdict may be a boolean here; return an action”. The kernel’s Lua answers a boolean with the hook’s fallback, and the kernel holds true and false as the words of 1 and 0, which are actions, so a test of the word cannot tell them apart.
    • Arithmetic on nil or a boolean, and an ordered comparison of a value that is not a number: “attempt to perform arithmetic on a nil value”, “attempt to compare a context with a number”.

    How a program file becomes a program

       lunatik bpf -o filter.bpf.o filter.bpf.lua               on the host

   filter.bpf.lua
   +----------------------------------------------------+
   | the body       runs once, now, on the host         |
   |   map.array(counts, {...})       --> a map         |
   |   xdp.program(fn, {...})         --> a program     |
   | the function   compiled now, run later, per packet |
   +----------------------------------------------------+
          |
          | 1. lunatic, the Lua compiler of the kernel, compiles the file:
          |    the bytecode the kernel would run, integers only
          v
   the chunk of the program file
          |
          | 2. the Lua of the CLI (lua5.5) runs the body from that chunk;
          |    require finds bpf.xdp, bpf.tc, bpf.map and lunatik,
          |    then the kernel scripts under /lib/modules/lua/, or the
          |    --scripts directory
          v
   the programs and the maps the body declared
          |
          | 3. the translator turns each program function, and each Lua
          |    function it calls, into eBPF instructions; outside the
          |    subset, lunatik: file:line: reason, exit 1, no object
          v
   eBPF instructions, each one tagged with its Lua line
          |
          | 4. the object is written for the kernel lunatik.config names,
          |    with the offsets of the context fields read from its BTF
          v
   filter.bpf.o          installed as /usr/local/lib/bpf/luaebpf/filter.bpf.o

    A program file, <name>.bpf.lua, may declare several programs. Each is named by the name its constructor takes, or after the file, and lunatik run --dev attaches every one of them, as Compiled programs describes.

    lunatik bpf compiles for the kernel lunatik.config names, which make writes from the kernel tree Lunatik is built against. Three facts of that kernel change what compiles:

    • Linux 6.9 or later compiles a for whose bounds the program computes; an earlier kernel refuses it.
    • A kernel without efficient unaligned access refuses a read wider than a byte, from the packet or from a map value (#2047).
    • The object takes the kernel’s byte order.

    The offsets of the context fields come from the kernel’s BTF, /sys/kernel/btf/vmlinux unless --btf names another file, so a program that reads its context, or the packet, compiles only where that BTF is. Compiling for another kernel is in Program files. A TC program needs libbpf 1.3.0 or later on the machine that loads it.
